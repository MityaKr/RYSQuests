# 07 · Решения (ADR)

Формат: номер, решение, почему, что отвергнуто. Новые решения добавлять снизу, старые не переписывать (помечать «отменено ADR-N»).

## ADR-1 · Один Gradle-проект, два пакета (отменено ADR-23)
RYScore живёт пакетом `works.repka.ryscore` внутри jar RYSQuests, с запретом зависимостей от `rysquests`. Выделение в отдельный мод, когда появится второй потребитель. Отвергнуто: мультимодульный проект сразу (лишняя сложность сборки без второго потребителя).

## ADR-2 · ModDevGradle
Сборка через ModDevGradle. Отвергнуто: NeoGradle (тяжелее), Architectury (не нужен без Fabric в MVP).

## ADR-3 · Строковые id и один файл на квест
`ResourceLocation` для всех сущностей; один JSON на квест; порядок полей стабилен. Причина: git, генераторы, миграции. Отвергнуто: числовые id (FTB Quests), один файл на главу как основной формат (допускается как альтернатива).

## ADR-4 · Сервер авторитетен, прогресс в SavedData
Прогресс хранится в одном `SavedData` на сервер, ключ команда (UUID). Клиент получает снимок при входе и диффы. Отвергнуто: data attachments на игроке (неудобно для командного режима), хранение на клиенте.

## ADR-5 · Проверка задач по событиям, редкий тик с разносом
Где есть событие, используется событие; `observe`/`stat`/`visit` раз в 20 тиков с разносом по игрокам и кэшем хэша инвентаря. Отвергнуто: проверка каждый тик.

## ADR-6 · Миграции через `migrations.json`, применяются один раз, с архивом
Удаление никогда не теряет данные: записи уходят в архив. Отвергнуто: автоматическое угадывание переименований по похожести названий.

## ADR-7 · Автораскладка на клиенте с кэшем на диске
Слоёный алгоритм считается на клиенте в фоне, кэш по хэшу книги. Отвергнуто: раскладка на сервере (разные размеры экранов и свёртки у игроков), хранение координат в датапаке как обязательное.

## ADR-8 · Книга отправляется целиком и сжато один раз
При входе и `/reload`. Отвергнуто: ленивая подгрузка глав (сложнее, выигрыш мал при сжатии).

## ADR-9 · Награды выдаются по действию «Забрать»
Не автоматически, кроме режима, который автор включит позже. Причина: инвентарь полон, выбор `choice`, командные правила. Отвергнуто: авто-выдача по умолчанию.

## ADR-10 · Редактор в игре не в MVP
Авторский процесс это генератор; редактор после MVP. Файловый формат проектируется так, чтобы редактор мог его писать без потери порядка полей.

## ADR-11 · Концепт «Компаньон» не учитывается
Решение автора. Не проектировать под него специально; не блокировать (события и API позволяют добавить панель позже).

## ADR-12 · Темы через JSON в ресурспаке, nine-slice текстуры (отменено ADR-14)
Скругления и тени рисуются спрайтами, токены цветов тонируют. Отвергнуто: шейдеры для blur в MVP.

## ADR-13 · Мост к вьюеру рецептов как интерфейс, JEI первой реализацией (дополнено ADR-20)
Отвергнуто: жёсткая зависимость от JEI.

## ADR-14 · Интерфейс рисуется процедурно, тема состоит только из токенов
Отменяет ADR-12. Скругления, рамки, тени и бевели рисует `Draw` в пикселях устройства. `Theme` даёт примитивы `panel`, `card`, `plate`, `slot`, `hover`, `button`, `input`, `tab`, `chip`, `tooltipBox` и признак `beveled()` для Vanilla. Тема это JSON с полями `id`, `name`, `font`, `colors`, `metrics`, `effects`; раздела `textures` нет. Причина: формат уже работает в RYScope, углы гладкие на любом GUI Scale, для новой темы достаточно одного JSON. Отвергнуто: nine-slice через `blitSprite` (текстуры на каждую тему), свой формат темы.

## ADR-15 · RYScore повторяет контракты RYScope (отменено ADR-23)
Классы `works.repka.ryscore.ui.Draw`, `ryscore.ui.Loading`, `ryscore.ui.theme.Theme`, `ryscore.ui.theme.ThemeManager` с теми же именами классов и методов. Имена и значения токенов, а также цепочка запасных токенов берутся из RYScope, своих токенов не вводим. Внутри `ryscore` только классы Minecraft, без API NeoForge, иначе код не перенести в `common` RYScope. Дополняет ADR-1. Причина: библиотеку потом сливают простым переносом. Отвергнуто: свои имена и своя иерархия пакетов.

## ADR-16 · Исключение из правила Codec для тем (отменено ADR-23)
`Theme` читает JSON через Gson, как в RYScope. Тема это открытые словари токенов с запасными значениями, и кодек сломал бы слияние простым переносом. Исключение только для тем; данные квестов и сеть остаются на `Codec` и `StreamCodec`.

## ADR-17 · Одна выбранная тема на оба мода (отменено ADR-23)
Наши копии тем лежат в `assets/ryscore/ryscore_themes/`. Папка отдельная, потому что `ThemeManager` RYScope ищет `ryscope_themes` во всех namespace, и наши файлы там стали бы дублями в его списке. Если RYScope установлен, через отражение читается только `ThemeManager.get().id`, и по этому id тем же парсером читается файл `assets/<ns>/ryscope_themes/<имя>.json`, поэтому работают и темы из ресурспаков. Настройка темы в книге при этом скрыта. В состав входят Slate, Vanilla и Glass, потому что игрок RYScope может быть на любой из них. Отвергнуто: жёсткая зависимость; чтение токенов из объекта темы RYScope отражением на каждый вызов; сопоставление только встроенных тем.

## ADR-18 · Единицы интерфейса это пиксели GUI
Числа в макетах делятся на 2,2 (константа `DESIGN_SCALE` в `Theme`): слот 40 в макете это 18 GUI. Окно книги 1200×728 это 545×331 GUI, колонки 232 и 392 это 105 и 178. Три колонки помещаются на GUI Scale 2 и 3 при 1920×1080; на Scale 4 (480×270) работает компактный режим. Отвергнуто: считать пиксели макета пикселями GUI.

## ADR-19 · Поведение окон общее с RYScope
Окно открывается сразу, тяжёлый расчёт идёт вне кадра или порциями, внутри окна индикатор `Loading`. Окна не прыгают: верхний край закреплён, рост только вниз. Длинных подсказок в строке внизу нет, вместо них значок «i» и подсказка при наведении. Шапка не дублирует то, что уже видно. Вкладки вместо стрелок «1/7». Панели обходят чужие области экрана. Причина: решения приняты в RYScope после жалоб игроков, и игрок не должен видеть шов между модами.

## ADR-20 · Отдельного моста к RYScope нет
Дополняет ADR-13. С RYScope в игре всегда есть JEI, а его `IRecipesGui.show` открывает окно RYScope, поэтому достаточно `JeiBridge`. Компиляция против минимальной версии JEI 19.42.0.379. С RYScope JEI стартует в фоновом потоке `RYScope-JEI`: `onRuntimeAvailable` и регистрация только сохраняют ссылки, без GL, мира и экранов. Отвергнуто: `RyscopeBridge` с жёсткой зависимостью.

## ADR-21 · Один `book.json` на книгу
Книга одна на сервер. Если `book.json` есть в нескольких namespace, берётся первый по алфавиту, об остальных предупреждает валидатор. Главы из `chapter_order` идут первыми, остальные по id. Причина: правило детерминировано и видно в отчёте, а настройки книги не имеют смысла складывать. Отвергнуто: слияние полей из нескольких файлов; выбор по приоритету датапаков (порядок между namespace не определён в `listResources`).

## ADR-22 · Большую книгу режет транспорт NeoForge
`BookSyncPayload` отправляется одним пакетом, `GenericPacketSplitter` сам делит его на части. Причина: штатный механизм с пределом 128 МБ, сжатая книга на порядки меньше. Отвергнуто: свой протокол частей из первого варианта плана.

## ADR-23 · RYSCore это отдельный мод
Отменяет ADR-1, ADR-15, ADR-16 и ADR-17. Общая основа семьи вынесена в мод `ryscore` (`C:\Projects\RepYS\RYSCore`), мы вкладываем его через jarJar с диапазоном `[1.0.0,2.0.0)` и объявляем обязательной зависимостью. Пакет `works.repka.ryscore` у нас не создаётся и классы кора не копируются: два мода с одним Java-пакетом не запускаются вместе (`ResolutionException`). Используем готовое: `theme.Theme`, `theme.ThemeManager`, `ui.Draw`, `ui.Loading`. Темы лежат в `assets/<ns>/ryscore_themes`, встроенные `ryscore:slate`, `ryscore:vanilla`, `ryscore:glass`; выбор темы общий и хранится в ядре, отражение за RYScope не нужно. Моды семьи общаются только через интерфейсы кора. Виджеты, доска поверх мира и разметка, которых в коре ещё нет, живут в `works.repka.rysquests`, а когда понадобятся второму моду, переносятся в кор. Папка кора только для чтения, правки идут через блок «Запрос к RYSCore». Отвергнуто: держать `ryscore` внутри нашего jar.

## ADR-24 · Сначала рабочий путь с книгой из FTB
Решение автора: как можно раньше увидеть квесты RepYS в игре. После M1 делаются минимальные версии M2, M3 и M6, из M5 берутся только типы, которые есть в книге (`stat`, `kill`, `visit`, награда `random`). Остальное из этих этапов и M4, M7, M8 идёт после проверки автором. Синхронизация с FTB это повторный запуск `/rysquests import ftbq`: результат пишется в автоматически подключаемый пак `config/rysquests/import/`, а `ftbq-ids.json` хранит соответствие id, поэтому повторный импорт их не меняет. Прогресс переносится отдельной командой из `world/ftbquests/`. Отвергнуто: постоянная двусторонняя связь с FTB Quests.

## ADR-25 · Решения, принятые при доводке книги
- Скрытые квесты (`hidden`) приходят клиенту и скрываются в интерфейсе, пока не откроются. Причина: книга отправляется целиком (ADR-8), а рассылать её заново при каждом открытии дороже, чем скрывать. Это оформление, а не защита от чтения данных.
- Раскладка карты считается в фоне и живёт в памяти, на диск не пишется: 2000 узлов укладываются быстрее 200 мс. Отменяет кэш на диске из ADR-7.
- В команде задачи общие, а награды каждый получает сам. С `team_mode: once` награду забирает первый, остальным она засчитывается.
- Закрепление на `P`: `A` и `G` над предметом перехватывает RYScope.
- Вид следует правилам RYSCore 1.2: разделы через `tabLine`, янтарь только у главного действия окна.

## ADR-26 · Команды через `TeamsApi`
В режиме `team` команду определяет `TeamsApi` из RYSCore. Если мода команд нет, работают наши `/rysquests team`. При слиянии и выходе прогресс переносит `TeamBridge`. Дополняет ADR-4.

## ADR-27 · Интерфейс совпадает с макетами
Просьба автора: «Юай должен совпадать с дизайном точно». Экраны считаются в пикселях макета через `Ui`, при окне 1280×800 и GUI Scale 2 они совпадают с `design/*.dc.html`. Заменяет перевод единиц из ADR-18, правила шапки и подсказок из ADR-19 и последний пункт ADR-25: где макет и правила кора расходятся, главнее макет.

Отступления от макетов, без которых нельзя:
- В шапке после вкладок макета стоит «Поток» и для операторов «Dev». В макете Main нет пути назад в Поток.
- Иконки и слоты остаются квадратными: в макете часть из них браузер сжал на несколько пикселей.
- Цвета только из токенов темы, поэтому в Потоке есть расхождения на 1–3 уровня от `#1e2029` и других значений.
- Пока нет данных: медиана времени в воронке, кто из команды что сделал. Эти места пусты или показывают прогресс своей команды.

## ADR-28 · Что снято с MVP
Решение автора. Этого нет в макетах, а по `10-design-rules.md` чего нет в макетах, того нет и в интерфейсе.
- Плотность интерфейса: противоречит точному совпадению с макетом.
- Перетаскивание доски стикеров: её угол задаёт общая настройка семьи (`Anchors` в RYSCore).
- Перенос `quest_links` из FTB: повтор квеста на другой странице потребовал бы нового поля и вида на карте. Импорт по-прежнему перечисляет такие ссылки в `import-report.md`.

## ADR-29 · Гайды простые
Решение автора: гайды в S1 как в макетах, страница это текст, картинки и ссылки. Маршрут по моду, шаги с условиями и 3D-структуры из `09-sections.md` не делаем.

## ADR-30 · Вкладки видов линией
Решение автора. Переключатель видов книги и вкладки Потока рисуются как в семье RYS: текст с линией под активной, без заливки. Это отступление от `Main.dc.html` и `Comfort.dc.html`, где у активной вкладки заливка. Вкладки Dev остаются как в его макете. Отменяет для вкладок видов общее правило ADR-27.

## ADR-31 · Экраны на масштабе RYSCore 1.6
Окна считаются в единицах `UiScale`, поэтому их размер не зависит от GUI Scale игры. При 1280×800 и авто-масштабе одна единица по-прежнему равна двум пикселям экрана, и сверка с макетами остаётся верной. Вкладки видов идут через `Kit.tabs`, их кегль 12 вместо 12,5 из макета. Доска стикеров ставится через `Anchors`: по умолчанию в левом верхнем углу, а не в правом, как в `Hud.dc.html`, потому что правый занят миникартой.

## ADR-32 · Главы внутри раздела Сюжет
Решение автора. Рейка разделов стоит слева у всей книги, а рейка глав Потока остаётся внутри раздела Сюжет и в других разделах не показывается. Если в `book.json` нет `sections`, рейки разделов нет и книга выглядит как сейчас.

## ADR-33 · Гайд изнутри без маршрута
Решение автора. `GuidePage.dc.html` и `Guides.dc.html` остаются эталоном раскладки, но из них убрано всё, что отброшено ADR-29:
- нет полосы маршрута, шагов, структуры, «Показать в мире», советов и «Если застрял»; страница это заголовок и текст со вставками;
- правая панель вместо «Куда двигаться» собирается сама из двух блоков: «Квесты по теме» и «Предметы на странице»;
- оглавление это один список страниц, без блока «Дальше в гайде»;
- в «Связано с гайдом» только квесты: число рецептов и сцен Ponder мод не знает;
- подпись внизу библиотеки заменена текстом для игрока, в макете была заметка для разработчика.

Гайд это отдельный файл `guides/<id>.json`, а не глава с `section: guides`, как подписано в макете. Ключи lang, файлы картинок и ссылки внутри текста проверяются на клиенте и видны во вкладке Dev: сервер не видит ресурсов и переводов.

## ADR-34 · Кастомные вкладки
Решения автора при S2.
- Атлас сборки это Матрица с полем `compact`: ячейки значками, номера эпох и легенда по `Atlas.dc.html`, но правая панель общая, как у `Mining.dc.html` и как записано в `09-sections.md`. Статистики, кнопки «Путь до него» и полосы «Ключевые предметы» нет.
- Фон картинки карточки это цвет `#rrggbb` в файле вкладки (`art`). Исключение из правила токенов: это содержимое автора сборки, как иконки предметов.
- Страница карточки это ссылка на гайд или на вкладку на шаблоне «Страницы». Такая вкладка может не стоять на рейке.
- Условие отметки карточки работает как скрытый квест в главе вне Сюжета: у него уже есть события, опрос и командный прогресс.
- Подписи внизу макетов Mining и Cards были заметками для разработчика; вместо них необязательный ключ `<title>.hint`.

## ADR-35 · Куда пишет редактор и как он работает на сервере
Решение автора: редактор работает и в одиночной игре, и на выделенном сервере.
- Файлы пишет сервер в папку из настройки `editorFolder` (общий конфиг), по умолчанию `config/rysquests/pack`. Папка устроена как пак (`data/`, `assets/`) и всегда включена. Для сборки на KubeJS указывается `kubejs`, тогда папку отдаёт сам KubeJS. Путь за пределами папки игры игнорируется.
- Сохранять могут только операторы (уровень 2). Сервер проверяет всё заново и пишет только строки сохраняемого гайда.
- Сервер не умеет раздавать ресурсы, поэтому переводы и картинки из папки редактора, на которые ссылается книга, идут вместе с книгой и поверх ресурсов клиента. Сохранённое сразу видно всем игрокам. Дополняет ADR-8. При выпуске сборки папка едет в сборке как обычно.
- После сохранения сервер перечитывает только книгу. Если новый файл не виден (первое сохранение, чужая папка), делается полная перезагрузка данных.
- Картинка берётся из последних снимков папки `screenshots/`, уменьшается до ширины 960 и копируется в `assets/<ns>/textures/guides/`.
- Перетаскивание предмета заменено списком инвентаря: у окна книги нет инвентаря, из которого можно тащить.

## ADR-36 · Конструктор вкладок
Решения при S4. `SectionEditor.dc.html` эталон раскладки; отступления:
- Порядок пунктов рейки, строк, столбцов и способов меняется кнопками, а не перетаскиванием.
- Предмет выбирается из инвентаря, а при вводе в фильтр из всех предметов игры.
- Вкладки свойств «JSON» и кнопки «Группы» нет: группы задаются списком на вкладке «Вкладка», файл можно открыть обычным редактором.
- Условие отметки карточки в конструкторе задаётся только достижением. Условие другого типа сохраняется как есть и правится в файле.
- Порядок рейки пишется в `book.json` папки редактора, в namespace уже существующего файла книги.

## ADR-37 · Магазин и валюта
Автор поручил решить самому.
- Валюта и титулы живут в RYSQuests. Другим модам они пока не нужны, и выносить их в RYSCore можно будет позже без смены формата.
- Лимиты сбрасываются по времени сервера: в полночь для `daily`, в полночь понедельника для `weekly`, как подписано в `Shop.dc.html`.
- Кошельки: личный и казна команды. Награда `currency` с `team_mode: once` идёт в казну, иначе в личный кошелёк. Тратить из казны может любой участник команды.
- Сделка это файл `shop/<id>.json`, а не запись в главе, как подписано в макете. Состояние магазина маленькое и уходит игроку целиком при каждом изменении.
- Залитая акцентом кнопка на экране одна: «Купить за N» на панели. В макете акцентом залита ещё кнопка на выбранной карточке, но это нарушает правило из `10-design-rules.md`.

## ADR-38 · Достижения
- Источники счётчиков проверены по коду: `kill` считается по событию смерти, `stat` читает статистику игры и потому видит прошлое, `item` проверяет инвентарь, `advancement` срабатывает один раз. Для достижения годятся они; задача со сдачей предметов или галочкой не имеет смысла.
- Каждый уровень это скрытый квест с той же задачей и своим порогом, как условия карточек в ADR-34. В режиме команды счётчик общий, как у квестов, поэтому блока «В команде» из `Achievements.dc.html` нет.
- Награды выдаются сразу, без кнопки; тем, кого не было в игре, при следующем входе.
- Титул показывается перед именем в чате и списке игроков. Рамки профиля нет: профиля в моде нет.
- Цвета медалей взяты из токенов темы: своих токенов медалей в RYSCore нет.
- Правая панель шириной 320, как записано в макете. В браузере макет сжимает её до 230 только из-за длинной служебной сноски внизу, которой в игре нет.

## ADR-39 · Редактор квестов
- Файл квеста пишется туда, где квест уже лежит: сервер перед записью читает пути из менеджера ресурсов. Новый квест попадает в папку главы, имя файла это последний сегмент id.
- Квесты из общего файла `_quests.json` редактор отказывается писать: при записи отдельным файлом id задвоился бы.
- Сохранённый квест из редактора не удаляется: файлы нельзя удалять, а из чужого пака не получится. Delete убирает только несохранённые.
- В `Editor.dc.html` нет создания главы, а приёмка требует главы из десяти квестов. Добавлена кнопка «+ Глава» под деревом файлов.
- В макете сказано «Горячая перезагрузка включена». Наблюдателя за файлами нет, внешние правки приходят с `/reload`, поэтому в подсказке написано именно так.
- Дерево файлов и поля id нарисованы шрифтом Inter: IBM Plex Mono из макета в RYSCore нет, а шрифты берутся только из темы.
- Формы есть у встроенных типов задач и наград. `choice`, `random` и типы других модов правятся на вкладке JSON: форму для вложенных наград макет не описывает.

## ADR-40 · Рецепты JEI, Ponder и 3D-структуры на страницах
Решение автора, отменяет запрет на 3D-структуры из ADR-29 и ADR-33.
- `[[recipe:]]` показывает рецепт так, как его рисует JEI, через публичный `createRecipeLayoutDrawable`: машины Create видны с анимацией. Без JEI остаётся простая сетка. В карточке квеста и в Потоке JEI рисует только то, что книга не может прочитать сама, полоска из макета остаётся.
- Фон рецепта это фон категории JEI, он светлый и токенами темы не управляется.
- `[[ponder:id]]` открывает обычный экран Ponder. Анимация Ponder внутри страницы отклонена: она идёт через внутренние классы и сломается при обновлениях.
- 3D-вид структур общий для семьи и живёт в RYSCore (`works.repka.ryscore.scene`, версия 1.7.0), RYSQuests и RYScope им только пользуются. Формат файла структуры совместим с `mapping` и `pattern` Patchouli.
- Блок структуры идёт по `GuidePage.dc.html`, окно выше, чем в макете (300 вместо 106): на странице места больше, а в 106 не разобрать постройку. Слои переключаются в заголовке блока.
- Импорт Patchouli пишет в папку редактора, а не в папку импорта FTB: тот импорт при повторе стирает свою папку.


## ADR-41 · Замечания после игры на сервере
Решение автора после игры с друзьями в теме Slate.
- Забранная награда, награда достижения, покупка и продажа сопровождаются тихим звуком, его слышит только сам игрок. Звук идёт с сервера, «Забрать всё» даёт один звук. Громкость регулируется ползунком «Игроки».
- Значки способов в матрице размером со значок в шапке панели (26), отступ 6 со всех сторон: в строке способа в «Атласе добычи» и в кольце компактной матрицы. Если способы не помещаются в ячейку компактной матрицы, ячейка рисует кольца из макета (значок 16).
- Цвета уровней достижений берутся из `Achievements.dc.html` (золото `#f0c53d`, серебро `#c9c9cf`, бронза `#b87333`) и одинаковы во всех темах, это исключение из правила «цвета только из темы». Раньше бронза строилась из акцента и была похожа на золото.
- Кольца медалей рисуются одной рамкой, а не двумя кругами: при масштабе интерфейса 3 круги округлялись по-разному и кольцо съезжало.
- В верхней полосе Dev кнопки ставятся справа налево и не накрывают друг друга: «Выйти из Dev», «Экспорт CSV», «Конструктор», «Редактор квестов». Сводка показывается, только если помещается. Кнопка выхода всегда видна, остальные пропускаются, если не помещаются перед вкладками.

## ADR-42 · История переходов в книге
Решение автора. Книга помнит, где был игрок, как браузер: раздел, вид, главу, квест, гайд и страницу.
- Backspace и боковая кнопка мыши «назад» возвращают на прошлое место, например с другой страницы гайда на страницу, куда привёл квест, а затем к самому квесту. Пока активно поле ввода или открыт редактор, Backspace работает как обычно.
- На странице гайда и вкладки «Страницы» слева от значка появляется кнопка со стрелкой возврата, без подписи, с подсказкой при наведении. Это отступление от `GuidePage.dc.html`. Кнопка видна, только если есть куда возвращаться. Стрелки ← и → справа по-прежнему листают страницы.
- История записывается в конце кадра, после того как виды сами поправят состояние, и хранит до 64 шагов.

## ADR-43 · Закрепление и переключатель на карте
Решение автора.
- Закреплённый квест на карте носит в правом верхнем углу круглый значок с булавкой. В макете `Main.dc.html` значка нет.
- Кнопка закрепления в карточке квеста и в Потоке показывает булавку вместо квадратика, закреплённый квест подсвечен акцентом.
- Переключатель рядом с названием главы называет действие, а не текущее состояние: «развернуть всё», а в развёрнутом виде «свернуть пройденное». В макете было «авто-раскладка».

## ADR-44 · Раскладка главы блоками
Решение автора: главы, импортированные из FTB Quests, складывались в столбцы до 66 квестов.
- Квесты без подглавы образуют главный путь: столбец на каждую глубину цепочки зависимостей, все столбцы по центру одной горизонтальной линии. Если на одной глубине больше шести таких квестов, открывается второй столбец той же глубины. Квесты, от которых идёт путь дальше, стоят в середине столбца.
- Подглава раскладывается как блок. Квесты одной глубины идут сеткой: по три в ряд, а у большой подглавы столько колонок, чтобы блок был ближе к квадрату. У подглавы с квестами разной глубины каждая глубина стоит в своей колонке.
- Блок висит выше или ниже главного пути у шага, от которого зависит, с той стороны, где ближе к линии; при равенстве стороны чередуются. Блок может сдвинуться вправо вдоль пути, если там свободно: сдвиг на колонку стоит дешевле, чем ярус дальше от линии. Квест вне блока, который от него зависит, всегда остаётся правее блока.
- Глава без главного пути, как «Летопись» и «Начало», ставит блоки рядом полками до десяти колонок в ширину, в порядке подглав главы.
- При раскладке резервируется место под подпись рамки и под выделенный квест, он крупнее обычного: подпись больше не уходит под узел.
- Зависимость, которая ведёт в подглаву снаружи, рисуется одной линией к боковой стороне рамки: сразу вниз или вверх в промежутке за источником, затем к рамке. Линии к каждому квесту сетки прошли бы через соседние узлы.
- Глава, которая помещается в поле карты, стоит в его середине. При открытии главы карта по вертикали центрируется на первом интересном квесте, а если всё пройдено, на первом квесте главы.
- Штрих рамки не тоньше пикселя экрана при любом зуме: раньше при отдалении часть штрихов пропадала.
- Список глав прокручивается перетаскиванием левой кнопкой. Нажатие на список ждёт отпускания: клик открывает главу, перетаскивание её не открывает.
- `layout.x` и `layout.y` по-прежнему ставят квест на ручное место. Формат данных не менялся. Раскладка считается в памяти по хэшу книги, новая версия мода сразу раскладывает по-новому. Редактор квестов использует ту же раскладку.

## ADR-45 · Ряд наград в карточке квеста
Решение автора: при многих наградах кнопка «Забрать» уезжала, а текст опыта её перекрывал.
- Награды-предметы и варианты выбора идут ячейками и переносятся на следующий ряд, а не обрезаются.
- Опыт показывается ячейкой с ванильным пузырьком опыта и числом. Уровни это или очки, видно в подсказке при наведении.
- Остальные награды словами, например монеты, идут после ячеек, а если там меньше 90 пикселей, то с новой строки.
- Кнопка «Забрать» стоит справа в последнем ряду, если помещается, иначе отдельной строкой под наградами. Отступление от `Main.dc.html`, где кнопка всегда в ряду ячеек.

## ADR-46 · Паритет с FTB Quests и правки после аудита
Задача автора: всё, что есть в FTB Quests и Heracles, плюс удобство, логика и производительность.
- Ссылки на квесты: поле главы `links`, квесты других глав видны на её карте с подписью «↗ из главы N», клик открывает квест в его главе, назад по Backspace. Импорт переносит `quest_links` FTB (в книге RepYS их около 125, раньше терялись).
- Задача на опыт `rysquests:xp` (`levels` или `points`, `consume` для сдачи кнопкой) и режим `craft` у задачи на предмет (скрафченное и выплавленное после открытия квеста). Импорт переносит задачу `xp` FTB и флаг `only_from_crafting`.
- Повторяемый квест больше не закрывает зависящие от него квесты между раундами: прогресс хранит `times`, зависимость считается выполненной при `times > 0`, а для старых сохранений и при заданном `next_at`. Повторяемый квест без перезарядки, пройденный до этой версии, следов не оставил и откроет зависимые после следующего выполнения. В режиме команды новый раунд очищает отметки о наградах у всех участников, чтобы никто не нёс их в следующий раунд. Квест, вернувшийся после перезарядки, снова считается без ожидания других изменений. Общий список открытых квестов команды не учитывает стадии, их проверяют для каждого игрока отдельно.
- Проверка книги предупреждает о повторяемом квесте с задачей на статистику, достижение или посещение и о ссылке главы на неизвестный квест.
- Карточка квеста показывает награды-команды, таблицы добычи и скрипты словами и всегда даёт «Забрать» у выполненного квеста. «Забрать» в Списке у квеста с невыбранной наградой открывает квест и подсвечивает варианты. Жидкость и опыт со сдачей получают кнопку «Сдать». Книга проверяет предметы тем же правилом, что сервер, с компонентами, и считает «Сдать всё готовое» по всей книге.
- Закреплённый квест после выполнения не занимает место в лимите, а выполненный неповторяемый уходит из закреплённых при следующем закреплении; при упоре в лимит приходит сообщение. «Сдать всё готовое» проверяет каждый квест прямо перед сдачей, чтобы ни один не оплатился наполовину, сообщает, сколько сдано на самом деле, или что сдавать нечего, и даёт тихий звук.
- Магазин продаёт только из основного инвентаря и только предметы без своих данных: не берёт надетое, повреждённое, зачарованное, переименованное и контейнеры с содержимым.
- Скрытый квест не называется по имени, пока не открылся: в строке «требует» и в подсказке «ждёт» он «???». Открывшийся скрытый квест даёт уведомление о выполнении. Закрытый узел на карте пишет, сколько ещё нужно, с учётом «любой» и «N из», время перезарядки или что нужна стадия.
- Импорт ставит задачу-заглушку, которая не выполняется, квесту, у которого не перенеслась ни одна задача: иначе он выполнялся бы сам или по одному клику и раздавал награды. Квест ждёт ручной правки, отчёт импорта его называет.
- Ограничение: режим `craft` считает событие крафта и выплавки игры; при шифт-клике, когда в инвентарь помещается не всё, игра сообщает полное число, и часть может посчитаться дважды. Сдача опыта засчитывает то, что действительно ушло у игрока, даже если другой мод изменил списание.
- Производительность: раскладка текста кешируется по тексту, ширине, виду, книге и языку, слова одного стиля рисуются одной строкой, строки вне обрезки пропускаются. Счётчики глав, значок гайдов, «Сдать всё готовое» и подписи задач считаются по версии прогресса, а не каждый кадр. Сервер пересобирает список открытых квестов только при выполнении квеста или смене раунда, а не на каждом шаге прогресса; теги предметов не создаются заново на каждой проверке; убийства и крафт фейк-игроков не считаются. Подписи капсом рисуются одной строкой. Сборка на RYSCore 1.8.0: кеш ширины текста (1.7.5) и пакетная отрисовка фигур и текста одним вызовом. Своей отрисовки мимо GuiGraphics в RYSQuests нет, сбросы пачки не нужны. Версия сетевого протокола поднята до 9: старый клиент не разберёт книгу с новыми полями, поэтому он получает понятный отказ при входе, а не пустую книгу.


## ADR-47 · Подсказка у обрезанного текста
Пункт 6 вердикта по задаче автора, общее правило семьи (записано в RYSCore/CLAUDE.md).
- `Ui.labelFit`, если текст не поместился, показывает при наведении подсказку с полным текстом. Так работают узлы карты, рейка глав, Список, Поток, «Что дальше» и остальные экраны.
- Прямоугольник подсказки переводится через текущую матрицу относительно начала кадра, поэтому на карте с любым зумом подсказка попадает в узел.
- Подсказка предмета под курсором главнее текстовой. Для текста на объекте, который сам объясняет себя при наведении, есть `labelFitPlain` без подсказки.

## ADR-48 · Импорт FTB без потерь и порядок в формате
Решение автора по вердикту пункта 5 («Импорт и формат»). Поля FTB Quests сверены по байткоду версии 2101.1.36.
- Импорт переносит всё, что движок уже умеет: награды command (как есть, с уровнем прав FTB: `permission_level` становится `as_server` с `level`, старый `elevate_perms` уровнем 2), loot (как случайная из таблицы), gamestage (кроме снятия стадии), advancement (как команда `advancement grant`); задачи advancement (без критерия), fluid (объект `{id, amount}` версии 2101 или старая строка, сдача, 1000 по умолчанию), biome, location (та же область блоков: у задачи посещения появилось поле `size`), gamestage (в `stage_required` квеста). `hide_until_deps_visible` не переносится: в FTB такой квест появляется вместе с зависимостями, а скрытый здесь ждёт их выполнения. Пустой вес таблицы добычи не переносится, об этом есть строка в отчёте. Отчёт начинается с итога по типам, содержимое таблиц не считается повторно. Пустой предмет, предмет-строка из книг 1.20 и убийство по тегу больше не обрывают импорт: первые два читаются или пропускаются с заметкой, убийство по тегу пропускается с заметкой.
- Награда-команда понимает подстановки FTB Quests: `{p}`, `{x}`, `{y}`, `{z}`, `{quest}`, `{chapter}`, `{team}`, `{team_id}`, `{long_team_id}`, `{member_count}`, `{online_member_count}`. Неизвестное имя остаётся как есть, поэтому JSON-текст в команде не ломается. Отличия от FTB Quests: `{team}` и `{team_id}` дают id команды, а не название, `{quest}` и `{chapter}` дают id, а не шестнадцатеричный код. Вывод команды всегда скрыт.
- `accumulate` остаётся в формате, чтобы старые файлы читались, но работает как `observe`; проверка книги предупреждает, редактор его не предлагает.
- Поле главы `requires` стало проверкой книги, а не замком: квест главы с `requires` не должен зависеть от квеста главы вне её цепочки. Главы без `requires` не проверяются, чтобы импортированные книги не шумели.
- Не делаем: замок главы, ящики добычи с мобов, барьеры, предмет-книгу, картинки на карте, задачу «взаимодействие» (решение по вердикту). Команды из чужих книг выполняются как написаны, перед выпуском их стоит просмотреть.

## ADR-49 · Редизайн книги: данные и сеть
Решение автора: книга переделывается по итоговому дизайну `_audit/book2/final/plan.md` («С первого взгляда»), автор разрешил решать по нему без согласования. Это шаг 3 «Порядка работ»: данные и сеть мода, без экранов. Формат описан в `02-data-format.md`, протокол сети поднят до 10.
- Новые необязательные поля. Книга: `epochs` (названия эпох; эпоха, созданная импортом FTB, помечена `imported` и автовыбором формы не считается), `map_form` (`auto`, `serpentine`, `spiral`, `generator`, `galaxy`), `published` (по умолчанию открыта, чтобы RepYS не закрылась). Глава: `off_map`. Квест: `milestone` (старое `size: 2` читается как веха, `size` больше не пишется), `draft`, `archived`. Достижение: `archived`. Порядок полей при записи стабилен, `book.json` тоже пишется в порядке документа и больше не теряет поля при сохранении рейки.
- Черновик и архив игрокам не отправляются и сервером не считаются. Квест, который их ждёт, у игроков не откроется: это замечание проверки (`requires_draft`, `requires_archived`), а не особое правило, чтобы клиент и сервер считали одинаково.
- Замок публикации: закрытая книга игрокам не рассылается, они получают пустую книгу с названием; сервер не считает их прогресс и не принимает их действия и покупки. Операторы (права 2) получают книгу целиком. Пакет `PublishPayload` пишет `published` в `book.json` папки редактора и перезагружает книгу.
- Готовая раскладка `rysquests/layout.json` едет внутри книги. Её проверяет отдельный хеш `layoutHash`: только то, от чего зависит карта, без текстов, задач, наград, черновиков и архива. Клиент игрока приходит к тому же хешу по своей книге. Пишет файл клиент оператора (`LayoutSavePayload`), сервер принимает раскладку только для книги, какая она сейчас. Команда `/rysquests layout bake` просит клиент оператора посчитать. Расчёт делает карта через крючок `ClientLayout.setBaker`.
- `layout.x`, `layout.y` ставят квест на ручное место только с `pin: true`; без него координаты только запомнены. Отступление от ADR-44: так импорт хранит положение квеста из FTB (клетка FTB равна 24 единицам), и нынешняя карта его не читает. Редактор всегда пишет ручное место с `pin`, файлов с координатами без `pin` в книгах нет.
- Глава последнего выполнения хранится на игрока (`last_chapter`), обновляется только его собственным действием и едет только ему в `ProgressPayload`.
- Строка истории магазина знает, была ли операция из казны (`treasury`).
- Сохранение редактора несёт версию главы, с которой начата правка (`BookHash.chapterVersion`: глава и все её квесты). Сервер отклоняет сохранение поверх чужих правок, называя оператора, который сохранил главу последним, или что главу изменили файлами; повторное сохранение пишет поверх (`force`). Версия на главу, а не на книгу: правка другой главы не конфликт.
- Причины словами: `EditorResultPayload` и `ShopResultPayload` несут ключ lang и аргументы. Отказ в награде, итог «Сдать всё готовое», лимит закрепления идут одним пакетом `BookMessagePayload` для строки сообщений книги (картинка 48) и, как раньше, над хотбаром.
- Награда-предмет, которой нет места в инвентаре, больше не падает на землю: она остаётся «к получению» с причиной «нет места», как обещал формат. Случайная награда и таблица добычи по-прежнему могут упасть: их исход неизвестен до броска; достижения тоже, у них нет кнопки «Забрать».
- Импорт FTB. Файл, который не прочитался, останавливает импорт до записи и называется с номером строки; импорт можно повторить без этого файла, кроме `data.snbt`. Глава, которую не удалось перевести, называется так же. Задача, которой у нас нет, становится галочкой, квест черновиком; квест без выброшенной награды тоже черновик. Это заменяет заглушку-скрипт из ADR-46: черновик игроки не видят, поэтому галочка безопасна и удобна для правки. Перенесённая книга закрыта. Отчёт по видам (`ImportReport`) и пакеты мастера переноса в обе стороны (`FtbqImport*Payload`); команда идёт тем же путём.
- Правило автовыбора формы (раздел 5 плана) записано чистой функцией `MapForms`: «мало связей» это не больше 5 % зависимостей между квестами, ведущих из главы в главу. Проверено на книгах: RepYS выходит серпантином, перенесённая ATM10 галактикой.
- Исправления из ревью: необязательные квесты не входят в счёт главы (`BookCounts`), «Сдать N» сдаёт только свою задачу (индекс задачи в пакете, `-1` для всего квеста), награды в Потоке переносятся строками, а не обрезаются, «Что дальше» не засчитывает предметы в инвентаре для режима `craft`, прогресс задач и забранные награды переезжают вместе со своими задачами при перестановке, добавлении и удалении в редакторе (`ProgressRemap`).
- Клавиша G («Сдать всё готовое») удалена, K, P, B остаются. Цвет уровня достижения задаёт место (`Achievement.medal`): последний золотой, перед ним серебряный, остальные бронзовые.
- Черновик редактора хранится на диске клиента по серверу или миру (`EditorDrafts`, `ClientDrafts`); экран его пока не использует.

## ADR-50 · Карта «Полотно»: формы, движок и экран
Решение автора: делаем по итоговому дизайну, отступления от исходников на python решаем без согласования. Движок в `client/layout` (`MapBook`, `Wheels`, `Packer`, `Forms`, `LayoutEngine`, `CanvasLayout`), полотно в `client/canvas` (`MapCanvas`, `MapLayouts`), экран `client/screen/MapView` во вкладке «Карта».
- Четыре формы перенесены из утверждённых раскладок (`quests-layouts-fable`, `quests-hub-fable`, `book2/final/src/atm_forms.py`). Колёса книги с флагом `optional` строятся по нему, книги, где побочных меньше 25 % (ATM10, 12 %), читаются как дерево: опора это квест, от которого кто-то зависит.
- **Галактика.** Рукава это полосы постоянной ширины (смещение поперёк линии, а не по радиусу), все рукава начинаются на круге не короче суммы их ширин, угол между соседними рукавами считается от половин их ширин. Если главы всё равно касаются, рукава раскрываются сильнее (закрутка ×1,35, до шести попыток). В python полосы у ядра налезали друг на друга, а правило «области глав не пересекаются» этого не допускает. Образ тот же, закрутка чуть меньше, чем на `43`.
- **Ядро галактики:** первый по номеру раздел, если в нём не больше шести глав и остальных хотя бы вдвое больше; иначе главы, от которых зависят квесты других глав (если их не больше трети); иначе первая глава.
- **Генератор** и для книг с эпохами строится как в `atm_forms.py`: каждая глава своим кругом, круги по порядку книги на овальной спирали. Силовая раскладка из `quests-skilltree-fable` не берётся: она медленнее и раскладывает книгу каждый раз иначе после малой правки.
- Глава без эпохи в книге, где эпохи задал автор, на полотно не входит и стоит в сайдбаре в «Вне карты»; в книге, где эпохи создал импорт (галактика), такие главы это свой раздел «Без раздела» последним, и в сайдбаре тоже.
- `layout.json` получил необязательное поле `decor` (формы глав, орбиты, метки эпох, подписи, повороты ствола); раскладка без него считается неполной. Клиент держит раскладки по хешу книги в памяти и на диске (`rysquests/layout_cache`).
- Мини-карта появляется с уровня эпохи, как на картинке `15b` (в тексте плана с уровня главы): эталон картинка.

## ADR-51 · Проверка перед выпуском на копии сборки
Последняя проверка новой книги на копии RepYS (`run-repys`, сценарии `repys`, `upgrade_new`, командные `team_a`/`team_b`).
- Эпоха 0 означает «без эпохи». Книги до `off_map` (RepYS на RYSQuests 0.1.0) клали вступление и летопись в `epoch: 0`; теперь в книге с эпохами такие главы стоят вне карты, как с `off_map`. Хеш раскладки не меняется: он и раньше писал отсутствующую эпоху нулём.
- Обновление с 0.1.0: прогресс, забранные и ждущие награды, закрепления, кошелёк, история магазина и уровни достижений переходят без миграции, как на старой книге, так и после замены её новой книгой и `/reload` (id не менялись).
- Счётчик достижения на статистике игры показывается в её единицах: тики в часах или минутах, сантиметры в километрах или метрах, урон в десятых долях единицами (`28`: «18.4 из 50 км», «13 из 24 ч»).
- Кнопка сдачи пишет «Сдать: Электромеханизм ×8», а не «Сдать 8 электромеханизмов»: названия предметов других модов не склоняются, так же строятся история магазина и подпись продажи.

## ADR-52 · Круг повторяемого квеста в команде и право на казну
Решение автора 18.11 после ночной проверки (разбор `_shared/_audit/full-2026-11-18/E-rysquests-rysteams.md`, пункты 4 и 5). Меняет часть ADR-46 про новый раунд.
- Повторяемый квест в команде по-прежнему начинает новый круг, когда один участник забрал все свои награды. Что остальные не успели забрать, не пропадает: оно остаётся у каждого в личной записи `owed_rounds`, пока он это не заберёт, даже если новый круг уже идёт или закончился (тогда копится счётчик кругов). Пока запись есть, книга показывает игроку квест выполненным; забранное уходит из записи, повтор невозможен. Список открытых квестов команды, сдача задач и починка застрявших считаются по записи команды, поэтому должник помогает с текущим кругом.
- Казна команды тратится только с правом RYSTeams `spend_treasury` (по умолчанию лидер и офицеры, лидер меняет в матрице прав). Проверка идёт по UUID через `TeamsApi.can` и не требует открытого экрана: будущие блоки магазина будут тратить казну от имени владельца блока. Класть в казну (продажа, награда) право не нужно. Без права книга не предлагает платить из казны.

## ADR-53 · Предмет с компонентами в сделке и лимит на команду при переходах
Шаги М1 и М2 плана магазина (`_shared/_audit/shop/PLAN.md`, раздел 5), RYSQuests 0.2.6. Решение автора 18.11: схемы машин в магазин не идут (крафтятся из пустой схемы и контроллера), М1 остаётся общей возможностью.
- Предмет в `gives` может нести `components` (`DataComponentPatch`, как у награды-предмета) и выдаётся как есть. В `cost` компоненты запрещены проверкой книги: платят только простым предметом (`ShopService.pays`). Место в инвентаре считается по стекам того же предмета с теми же компонентами. В поиске кругов предмет с компонентами отдельный товар.
- Лимит на команду ходит за игроком. Уходящий (в том числе при роспуске) получает копию использованного командой и запись «учтено» в `counted_usage`. Вступающий добавляет команде только свои покупки сверх учтённого; повторное вступление ничего не удваивает. При слиянии использованное складывается, отмена слияния возвращает обе стороны. Перенос идёт при любом правиле команды о прогрессе: лимит защищает от двойной покупки, а не переносит прогресс.
- Почему так: это тот же класс дыр, что дюп наград в 0.2.4 («вышел, купил, вернулся»). Брать максимум при вступлении недостаточно для лимита больше 1, а сумма без учтённого считала бы одну покупку дважды.

## ADR-54 · Накопительная сделка и счёт поставки команды
Шаг М4 плана магазина (`_shared/_audit/shop/PLAN.md`, разделы 3 и 5), RYSQuests 0.2.7 (черновик).
- Сделка с `delivery: true` не платится сразу: предметы из `cost` сдаются частями в общий счёт, валюта из `cost` списывается при выдаче. Счёт `DeliveryLedger` лежит в `ProgressStore` (`deliveries`): владелец (команда или одиночка), цель, предмет, число. Цель это строка, сейчас id сделки; так счёт подойдёт и будущим «Испытаниям» (раздел 4.7 плана).
- Сдача берёт по каждой строке не больше недостающего, только простые стаки основного инвентаря. Выдача требует полных строк, платит монеты (свои или казна по праву `spend_treasury`, как в ADR-52), снимает одну норму. Излишек остаётся на следующий круг: он появляется только при слиянии или вступлении, и выбросить его значило бы потерять сданное.
- Правила команды. Главное: предметы между счетами только перемещаются, никогда не копируются, поэтому никакой порядок «вышел, сдал, вернулся» не даёт сдать одно и то же дважды (класс дюпа наград из 0.2.4).
  - Вступление: личный счёт целиком переходит команде и обнуляется. Повторное вступление ничего не добавляет.
  - Выход: ушедший ничего не уносит, даже если правило команды оставляет ему копию прогресса квестов. У команды остаётся всё.
  - Роспуск: счёт остаётся на записи команды; RYSTeams при возврате из архива заново вводит участников, и их личное сданное после роспуска вливается туда же.
  - Слияние: счёт слитой команды прибавляется к объединённой. Отмена слияния возвращает слитой команде не больше, чем у неё было до слияния и чем у объединённой ещё осталось; выданное за это время не возвращается никому.
  - Оператор: `/rysquests shop delivery reset <игроки> [сделка]` обнуляет счёт команды игрока и его личный.
  - Команды собственных команд мода названы по лидеру: счёт лидера и есть счёт команды, вступление лидера в свою команду ничего не двигает.
- Почему не копия, как у лимитов (ADR-53): лимит защищает от двойной покупки, и копия у ушедшего только запрещает. Счёт поставки это ценность: копия дала бы второй трофей.
- Сеть: состояние магазина несёт счёт команды только по сделкам-поставкам книги, версия протокола 11.

## ADR-55 · Ядро сделки без игрока
Шаг М5 плана магазина (`_shared/_audit/shop/PLAN.md`, разделы 4.1–4.6 и 5), RYSQuests 0.2.7 (черновик). Основа для блоков «Приёмщик» и «Выдача» (М6, М7); для игрока в книге ничего не меняется.
- Сделка живёт в `TradeCore`: `check` ничего не меняет и отдаёт план (сколько раз, чей кошелёк, чей лимит, чей счёт поставки) или ключ отказа, `execute` исполняет план в том же вызове на потоке сервера. Порядок отказов прежний: запрос, команда, право на казну, этап, квест, лимит, поставка, оплата, место. `deliver` сдаёт в счёт поставки команды только недостающее, с режимом «только посчитать» для честной симуляции вставки трубой.
- Кто торгует: `Trader` (UUID владельца, казна или свой кошелёк, этапы, потолок раз, сводная история). Игрок в книге: потолок 64, ровно столько раз, сколько просил. Блок (`Trader.owner`): без потолка, столько раз, сколько позволяют монеты, предметы, лимит и место (режим `fewer`, место ищется двоичным поиском по симуляциям). Право `spend_treasury` спрашивается у владельца по UUID при каждой сделке, игрок может быть не в сети. Сделка с этапом блоку закрыта, пока владельца нет в мире: этапы привязаны к игроку.
- Откуда и куда: `TradeSource` (`count`, `take`, только простые стаки) и `TradeSink` (`fits`, `put`, остаток возвращается вызывающему). Есть реализации для списка стаков игрока и для `IItemHandler` блока: источник считает по симуляции извлечения, приёмник по симуляции вставки слот за слотом, разные товары не делят один слот. У игрока не поместившееся падает под ноги, как раньше; блок получит остаток в `Outcome.leftover` и придержит его.
- История: сделки блока пишутся `ProgressStore.addShopSummary` в одну строку на сделку, валюту, кошелёк и знак; строка обновляется и поднимается наверх, пока между ними не пришла другая операция. Открытые строки не сохраняются: после перезапуска начнётся новая. Формат истории не менялся.
- Сеть: после сделки блока состояние магазина уходит участникам команды в сети не чаще раза в секунду на команду (`ShopBroadcast`, проверка в конце тика сервера, пустой набор ничего не стоит). Сделка игрока в книге по-прежнему шлёт состояние сразу.
- Закрытая книга блокам ничего не продаёт: без игрока нельзя проверить права оператора.

## ADR-56 · Блок «Приёмщик»
Шаг М6 плана магазина (`_shared/_audit/shop/PLAN.md`, разделы 4.1, 4.3–4.7), RYSQuests 0.2.7 (черновик). Первый блок мода.
- Регистрация в `block.ModBlocks`: блок `rysquests:shop_receiver`, предмет, сущность блока, меню. Рецепта в моде нет (рецепты даёт сборка, шаг Г9 с согласия автора), блок лежит во вкладке творческого режима «Функциональные блоки». Таблица лута отдаёт блок, кирка ломает быстрее.
- Логика без мира в `block.Receiver`, её гоняют юнит-тесты; сущность блока только держит её, планирует тик и красит лампу. Магазин блок видит через `ReceiverMarket` (на сервере `ShopService.tradeFor`, `checkFor`, `deliverFor`).
- Режим это программа (`ReceiverProgram`) в своём реестре по id: `rysquests:sell` и `rysquests:delivery`. В блоке хранится только id, поэтому «Испытание» добавится третьей программой без смены формата и без нового блока; id `rysquests:trial` занят, в окне это серая третья кнопка.
- Трубы: возможность `Capabilities.ItemHandler.BLOCK` с любой стороны, один пустой слот, только вставка, извлечения нет. Вставка проверяет предмет (только предмет сделки и только простой стак, как у ручной продажи) и прибавляет к счёту; симуляция отвечает так же, как настоящая вставка, поэтому трубы ничего не теряют. Чужой предмет блок не берёт, труба стоит.
- Продажа: буфер до 256 лотов каждого предмета, чтобы труба не насыпала бесконечную кучу; это потолок за секунду, а не ожидание. Расчёт одним запланированным тиком через секунду после первого поступления: все целые лоты одной сделкой, остаток лежит в буфере и сохраняется. При поломке и смене сделки целые лоты продаются, остаток выпадает предметами.
- Поставка: поступившее сразу уходит в счёт команды владельца, только недостающее по строкам (`TradeCore.deliver`), набранная строка не берёт ничего.
- Нагрузка (раздел 4.5): тикера нет. Вставка это проверка и сложение. Стоящий блок (красный или тёмный) ничего не берёт и смотрит на сделку снова не чаще раза в секунду и только когда в него стучатся. Окно, пока открыто, смотрит на блок раз в 5 тиков и шлёт вид только при изменении.
- Состояния (раздел 4.3): `WORKING` зелёный; `WAITING` (продажа, которая стоит ещё и монет, а их нет) и `FULL` (поставка набрана) жёлтые; `NO_TEAM` (монеты в казну, а команды нет), `CLOSED` (сделка закрыта, убрана, книга закрыта), `LIMIT` красные; `NO_OFFER`, `NO_OWNER` тёмные. Лампа на модели и строка окна говорят одно. Компаратор и уведомление владельцу не сделаны: компаратор это шаг М7, уведомление ждёт ответа автора на вопрос 17 плана.
- Защита (раздел 4.4): владелец это поставивший игрок (машина владельцем не становится; блок без владельца достаётся первому, кто его откроет). Окно открывают владелец и его команда, команда смотрится в момент открытия и каждого запроса. Ломают они же и оператор (`BlockEvent.BreakEvent`), прочность взрыва как у обсидиана. Автоматика модов ходит как `FakePlayer`: окно ей не открыть. Казну как получатель монет можно выбрать, только если у владельца есть команда; класть монеты в казну право не нужно (ADR-52).
- Сеть: `ReceiverStatePayload` (вид окна) и `ReceiverConfigPayload` (режим, сделка, казна, сброс счётчиков), версия протокола 12. Сервер проверяет каждый запрос: открытое окно, право на блок, существование сделки и её режим, наличие казны.
- Окно на Kit RYSCore (`ScaledScreen`) по макетам 04 и 05. Отступления от макетов: у владельца вместо имени команды пишется «команда» (имени команды нет в контракте `TeamsApi`), значок владельца это `USERS` (одиночного силуэта в наборе значков нет), лампа в строке состояния красится токенами состояний (`state.ok`, `state.warn`, `state.bad`), а не акцентом. NBT сущности блока записан простыми тегами, как у сущностей блоков игры.

## ADR-57 · Блок «Выдача», компаратор и уведомление «блок встал»
Шаг М7 плана магазина (`_shared/_audit/shop/PLAN.md`, разделы 4.2–4.6), RYSQuests 0.2.7 (черновик). Каркас блока из ADR-56.
- Регистрация в `block.ModBlocks`: блок `rysquests:shop_dispenser`, предмет, сущность блока, меню; без рецепта, во вкладке «Функциональные блоки», таблица лута и кирка как у «Приёмщика».
- Логика без мира в `block.Dispenser`, её гоняют юнит-тесты (`DispenserTest`). Настройки целиком в записи `DispenserSettings`: окно шлёт её всю, сервер проверяет каждое поле. Магазин блок видит через тот же `ReceiverMarket` (добавлены `buy` и `checkBuy` поверх `ShopService.tradeFor` и `checkFor`).
- Модель ограничений (решение по брифу дирижёра 17.11). Всё в монетах и штуках, времени нет (принцип автора):
  - «Потратить не больше X»: блок тратит не больше X монет с последнего сброса счётчика кнопкой «сбросить счётчик» в окне или со смены сделки. Не «за период»: период означал бы ожидание, а сброс оставляет решение игроку. Лотов за раз ровно столько, чтобы не выйти за X.
  - «Оставить на счету X»: лот покупается, только если после него на счету останется не меньше X. Считается по кошельку, из которого блок платит (свой или казна).
  - «Держать в инвентаре не больше N» (из плана и макета 06): блок докупает, пока там, куда он кладёт, меньше N штук товара. Достигнутый запас это цель, а не поломка: жёлтая лампа без уведомления.
- Порядок одной покупки как в плане: открытость сделки и лимит, право на казну, ограничения, симуляция вставки, списание, вставка (всё в `TradeCore`). Когда ограничение не даёт купить, блок ещё раз спрашивает ядро без места: красный отказ (сделка закрыта, нет права, нет команды) важнее жёлтого ограничения.
- Куда класть: сторона из шести или свой слот (9 ячеек). Ответ на вопрос 15 плана из брифа: свой слот трубы опустошают (возможность `ItemHandler` только на извлечение, с любой стороны). Если товар не поместился сбоку после оплаты, остаток ложится в свой слот, и блок сначала отдаёт его, а потом покупает снова; не влезло и туда, выпадает предметом. Ничего оплаченного не теряется.
- Казна: включить оплату из казны может только игрок с правом `spend_treasury` и только при команде у владельца; уже включённую может оставить любой из команды. Каждая покупка спрашивает право владельца заново (ядро, ADR-55): без права блок встаёт красным `NO_RIGHT`.
- Редстоун: выключатель «работать только при сигнале», `level.hasNeighborSignal` при каждой проверке. Без сигнала блок тёмный (`REDSTONE`).
- Тик: тикер сущности, проверка раз в 20 тиков со смещением по хешу позиции. Проверка это несколько сравнений и одна симуляция вставки, «держать не больше» считает слоты соседа только когда остальные условия прошли.
- Состояния (общий `ReceiverStatus`, раздел 4.3): добавлены `NO_RIGHT` (красный), `NO_SPACE`, `STOCKED`, `BUDGET`, `RESERVE` (жёлтые), `REDSTONE` (тёмный). Отказ ядра `no_right` теперь `NO_RIGHT`, а не `NO_TEAM`. Тексты строки состояния у каждого блока свои (`rysquests.<блок>.status.*`).
- Компаратор у обоих блоков, режим в окне: по состоянию (зелёный 15, жёлтый 10, красный 5, тёмный 0) или по заполненности (у «Выдачи» свой слот, у «Приёмщика» буфер продажи, формула сундука). Обновляется при смене состояния и при каждом изменении слота или буфера.
- Уведомление «блок встал» (вопрос 17 плана, решение дирижёра 17.11): у обоих блоков, выключатель в окне (по умолчанию включён). `NoticeGate` (без мира, `NoticeGateTest`) держит одно уведомление на блок: новое только на смену состояния на жёлтое или красное, кроме набранного запаса; состояние, которое прошло до отправки, уведомления не даёт. Владельцу не чаще раза в минуту, несколько блоков сразу идут одним уведомлением «встали N блоков магазина». Владелец не в сети получит его при входе, если блок всё ещё стоит. Загруженный блок не сообщает заново то, что было до перезапуска; сами ожидающие уведомления не сохраняются. Клиент показывает его через `ui.Notice` RYSCore (карточка с предметом блока, причина, сделка, координаты; красные состояния красятся `bad`).
- Сеть: `DispenserStatePayload`, `DispenserConfigPayload`, `BlockNoticePayload`; у `ReceiverConfigPayload` и `ReceiverView` добавлены режим компаратора и выключатель уведомлений. Версия протокола 13.
- Окно «Выдачи» на Kit RYSCore по макету 06. Отступления: стороны выдачи названы направлениями («Снизу», «С севера», «Свой слот»), а не именем соседнего блока, у стороны без инвентаря пометка «нет инвентаря»; строка состояния без счётчика «за последнюю минуту» (времени блок не считает); внизу правой колонки обоих окон раздел «Блок» (компаратор и уведомления), которого в макетах 04–06 нет; в сводке строка «В своём слоте», когда там что-то лежит.

## ADR-58 · Поля магазина 0.2.7 в редакторе книги
Шаг М9 плана магазина (`_shared/_audit/shop/PLAN.md`, раздел 5), RYSQuests 0.2.7 (черновик). Панель товара на вкладке «Магазин» редактора (картинка 39) получает свойства сделки, которые появились в 0.2.6 и 0.2.7. Отступление от макета 39 (ему новых полей не хватает), решение дирижёра по брифу М9.
- Порядок панели: название, «Тип», «Игрок получает» (компоненты, 0.2.6), «Цена», переключатель «Поставка» (только у покупки), строки «Сдать поставкой» с полем числа (или «Игрок отдаёт ещё», если предметы цены остались после выключения поставки), «Раздел», «Открывается: Сразу | После квеста | После победы» со списком вех или боссов, «Строка закрытой карточки» (видна, только когда сделке есть чего ждать), «Лимит» с «Чей лимит» (0.2.6), внизу заметки о проблемах.
- Все правки идут через `editor.OfferEdits` без экрана: каждая меняет только своё поле и сохраняет остальные (`icon`, `stage`, `stage_title`, `lock_text`, `delivery`, компоненты, вторую валюту и её название). До 0.2.7 цена и список предметов переписывали сторону сделки целиком, и предметы поставки или жетон вместо монеты терялись бы.
- Правила поставки как у проверки книги (ADR-54): включается, только если есть предмет сдачи (иначе первой строкой ставится предмет из руки, простой), последнюю строку убрать нельзя, продажей поставка не становится (кнопка «Игрок продаёт» серая с подсказкой). Выключенная поставка оставляет предметы в цене: это честная сделка «предметы и монеты сразу», а не потеря.
- «После победы» это первый уровень достижения, у которого задача `kill` с одной сущностью (ADR трофеев, шаг М3); подпись по имени сущности из игры. Список вех тот же, что был (`opensAfter`).
- `lock_text` пишется ключом `shop.<ns>.<путь>.lock` (или уже имеющимся ключом сделки), текст в lang-файл папки редактора. Список ключей строк сделки один для клиента и сервера: `ShopOffer.textKeys()` (`title`, `category`, `lock_text`, `stage_title`).
- Проверка на месте: поле числа краснеет, пока введено не целое больше нуля, и ничего не меняет; заметки с причиной для поставки без предметов, поставки-продажи, предмета с компонентами в цене и строки закрытой карточки у сделки, которая открыта сразу.
- Попутно окно «Выдачи» меряет высоту правой колонки теми же числами, которыми рисует, и растёт, если колонка с разделом «Блок» дошла бы до нижнего отступа (сводка в режиме своего слота на строку выше).

## ADR-59 · Рецепты блоков магазина по умолчанию
Решение автора 18.11, RYSQuests 0.2.7 (черновик). Отменяет строку ADR-56 «рецепта в моде нет»: вне нашей сборки блоки должны крафтиться.
- Ванильные data-рецепты `data/rysquests/recipe/shop_receiver.json` (`IEI` / `IHI` / `ICI`) и `shop_dispenser.json` (`IEI` / `IDI` / `IRI`): железо `#c:ingots/iron`, изумруд `#c:gems/emerald`, воронка или раздатчик, деревянный сундук (как у воронки NeoForge, без ловушки) или редстоун `#c:dusts/redstone`.
- Id рецептов закреплены: `rysquests:shop_receiver` и `rysquests:shop_dispenser`. Сборка RepYS снимает их по id и ставит свои, менять id нельзя.
- Открытие в книге рецептов обычным достижением `recipes/redstone/<блок>` при получении воронки или раздатчика. Если сборка убрала рецепт, награда пропускает его молча (`ServerPlayer.awardRecipesByKey`).
- `ShopRecipesTest` держит пути, id, сетку и ключи (реестры в юнит-тестах не загружаются, поэтому без кодека рецепта).

## ADR-60 · Награда эпохи на карте, страницы «О книге», атласы для игроков
План `_shared/_audit/chronicle/PLAN.md` (варианты Б1.1 и Б2.1, макеты `04_epoch_reward.png` и `01_about_brand.png`), бриф дирижёра 17.11, RYSQuests 0.2.7 (черновик, выходит вместе с магазином). Формат в `02-data-format.md`.
- **Награда эпохи.** Эпоха в `book.json` называет квест (`{ "title": ..., "quest": ... }`). Квест остаётся обычным квестом: тот же id, прогресс и отметки забранных наград, поэтому миграций нет, а забранное раньше в главе «Начало» остаётся забранным. Карточкой главы он не показывается (карта, список, поиск, счёт главы, «Сейчас» как квест, ссылки «Откроет» называют его «наградой эпохи N»). Глава, где кроме наград эпох живых квестов нет, служебная: её нет в сайдбаре и на карте (`MapBook.rewardsOnly`). Из хэша раскладки такие квесты выпадают, раскладка RepYS после перехода устареет и перепекается в общей проверке.
- Награда ждёт (`EpochRewards.State.READY`), когда зависимости квеста выполнены и из задач осталась только галочка («Эпоха открыта» у RepYS). Галочки ставит сервер при получении: новое действие `QuestActionPayload.CLAIM_EPOCH` и «Забрать всё». Задача другого вида держит эпоху закрытой. Выдача идёт обычным `claim`, поэтому правила команд те же, что у квестов (ADR-52, ADR-53): что видит участник, считает одна функция `TeamRewards.memberView` для сервера и тестов. Уведомление о выполненном квесте для награды эпохи не показывается: игрок только что забрал её сам.
- Отступления от макета 04: значок награды это `SPARK` токеном `coin`, подарка в наборе `Icons` RYSCore нет (кор правит только сессия RYScope). Карточка стоит панелькой под плашкой эпохи, если плашка не видна, в левом верхнем углу полотна. В режиме «Список» карточки нет, клик по эпохе в сайдбаре открывает её только на карте и только когда награда ждёт.
- **«О книге».** Поле `about`: id гайда или список своих страниц (`BookMeta.About`). Название книги в шапке становится кнопкой со значком «i» (в компактной шапке кнопка только значок), страницы открываются поверх вкладки как настройки (`AboutView` поверх `GuidePageView`), вкладки гаснут. Точка горит, пока не прочитана ни одна страница; прочитанное своих страниц хранится как у гайда `rysquests:about`, сервер принимает его через `QuestBook.guideOrAbout`. «Гайд для начала» на «Сейчас» берёт эти страницы, а не первый гайд книги. Поля в настройках книги в редакторе пока нет: `about` и `quest` эпох пишет генератор, редактор их сохраняет нетронутыми.
- **Атласы для игроков.** Матрицы («Атлас сборки», «Атлас добычи») теперь видны игрокам во вкладке «Гайды», как остальные вкладки автора; править может только оператор. Это меняет решение автора из редизайна книги (`_audit/book2/final/plan.md`, таблица «Убрано»: «Атлас» и «Добыча» у игрока, матрицы остались в редакторе). Отдельного ADR у того решения не было, запись сохранена здесь. Причина: тексты книги ссылаются на атласы (находка плана, вопрос В.3), автор выбрал показать. Вкладку по-прежнему прячет список `sections` книги; замечание проверки «скрытая вкладка» теперь о вкладках вне этого списка, группа «Только в редакторе» на странице «Вкладки» убрана.

## ADR-61 · Статистика в общем прогрессе, полоска закреплённого уровня, ссылки на сайты
Баг автора 18.11 («Долгожитель», «Парашютист», «Бессмертный… почти» стоят у конца третьего уровня), задача автора про HUD и ссылки, RYSQuests 0.2.8 (черновик).
- **Причина.** Опрос задачи `stat` писал `max(значение, статистика опрашивающего игрока)`. Статистика у каждого игрока своя, а прогресс в режиме `team` общий, поэтому счётчик команды был числом лучшего участника, и другой игрок сдвинуть его не мог. На сервере RepYS у команды автора все три счётчика были числами напарника (19.66 км, 46 смертей, прошлые 49.2 часа без смерти), числа автора меньше (3.46 км, 37 смертей, 0.5 часа). Время без смерти к тому же никогда не сбрасывалось, хотя текст достижения обещает «смерть начинает счёт заново».
- **Решение (`StatCount`).** Значение задачи `stat` при общем прогрессе это сумма статистик всех, кто его делит: участники команды (RYSTeams или свои команды), в режиме `server` все игроки мира; так же складываются убийства команды. Значение только растёт, уход участника его не уменьшает. Серия, которую игра обнуляет (`time_since_death`, `time_since_rest`), считается иначе: самая длинная текущая серия среди участников, и значение идёт за ней вниз. Полученные уровни остаются полученными. Статистика участника не в игре читается из `world/stats/<uuid>.json` один раз за запуск, у вышедшего берётся его последний счётчик (`MemberStats`). Опрашивается так же раз в секунду.
- Окно достижений для серии показывает текущее значение, а не максимум по уровням.
- **Полоска закреплённого уровня.** Карточка закреплённого уровня достижения рисует под счётчиком полоску 3 пикселя от нуля до порога этого уровня, цветом медали этого уровня (`LevelSegments.token`), только одну. Данные те же, что приходят с сервера.
- **Ссылки на сайты.** Ссылка вида `url` пишется `[[url:https://…|подпись]]`, `[подпись](https://…)` или голым адресом; открываются только http и https с хостом. Клик ведёт как чат: при выключенных ссылках в настройках чата ничего, иначе ванильное окно подтверждения (`ConfirmLinkScreen`) с предупреждением, после него книга возвращается. Слова одной ссылки подсвечиваются вместе токеном `link`. Проверка гайдов считает такую ссылку верной.

## ADR-62 · Коллекции в достижениях
Вопрос автора 18.11 («почему полноценные коллекции не перенесли, нету функционала?»), RYSQuests 0.2.8 (черновик). В Летописи коллекция была квестом из нескольких задач `item` (`observe`), и игрок видел, что собрано. Достижение умело одну задачу, поэтому при переезде Летописи (генератор 7d1ca8f) 8 коллекций RepYS стали счётчиком `repys_collections.js` без списка. Формат в `02-data-format.md`, раздел «Коллекция».
- **Решение: одна задача-коллекция, а не несколько задач у достижения.** Задача `rysquests:collection` со списком `items` встаёт в то же поле `task`, что у остальных достижений, и `amount` уровней считает собранные предметы. Формат достижения не меняется (одна задача, уровни, награды), редактор хранит и пишет задачу как есть, порог уровня как всегда подставляет парсер. Несколько задач у достижения потребовали бы второго вида уровней («любые N из M задач») во всей логике квестов, клиента и редактора.
- **Хранение отметок.** Парсер делает скрытый квест `<ns>:_achievements/<id>/_collection` с задачей `item` в режиме `observe` на каждый предмет. Отметки получаются обычным прогрессом задач: их опрашивает тот же код раз в секунду при изменении инвентаря, они общие на команду (каждый участник своим опросом поднимает запись команды, поэтому предмет засчитан, если побывал у кого-то из команды, как сумма по команде в ADR-61), копируются ушедшему по правилу копии прогресса команды (ADR-26, `TeamBridge`), складываются при вступлении и слиянии (`MigrationEngine.best`), отменяются вместе со слиянием, сохраняются и рассылаются диффами без новых полей в сохранении и в сети. Своё хранилище отметок понадобило бы повторить всё это заново.
- Уровень это квест с задачей `collection`, её значение при опросе равно числу отметок (`CollectionMarks.levelValue`): не больше порога и никогда не меньше, чем было. Опрос уровня видит отметки, поднятые в этом же опросе. Квест отметок исключён из `Achievement.isTierQuest`, сообщений о выполнении (клиент и лента команды) и событий не даёт, о сборе говорит уровень.
- **Окно.** Панель достижения показывает раздел «Коллекция · 5 из 8» и ячейку на каждый предмет: собранный с зелёной рамкой и галочкой в углу, несобранный под вуалью; подсказка предмета игры плюс строка «Собрано», «Ещё не собрано» или «Нужно 64 сразу, больше всего было 10». Карточка и уровни пишут «5 из 8» через число отметок. Закреплённый уровень на HUD рисует строку «Предметы коллекции 5 из 6» и полоску ADR-61 без изменений. Макета у раздела нет: ячейки и токены как у предметов в панели квеста (`slot.bg`, `slot.border`, `state.ok`, вуаль 0.55).
- Порядок списка значим (отметка по месту), новые предметы идут в конец. Квест отметок, выполненный до того, как список вырос, снова попадает в опрос, пока новые не собраны. Валидатор: `achievement_collection_amount` (порог больше списка), `achievement_tier_name` (имя уровня с `_`), `collection_outside_achievement` (задача в обычном квесте не двигается).
- **Перенос отметок RepYS (делает генератор).** Мод не читает чужое хранилище: формат `repys_col` знает только скрипт сборки. Мод даёт `QuestsApi.collect` (в KubeJS `RYSQuests.collect(server, owner, achievement, item)`) и `RYSQuests.progressOwner(player)`: отметить предмет для команды или игрока, в игре он или нет; повтор ничего не меняет. Владелец в режиме `team` это `TeamsApi.teamOf`, тот же id, под которым скрипт хранил отметки команды. Генератору: 8 коллекций с `rysquests:script` перевести на `{"type": "rysquests:collection", "items": [...]}` (предмет с числом больше 1 объектом `{"item": …, "count": n}`, как `sky_captain`), уровень оставить (`gold`, `amount` равно числу предметов), `repys_collections.js` заменить скриптом переноса ниже и оставить его на одну-две версии. Значение уровня, которое скрипт уже записал («5 из 8»), сохраняется и не уменьшается.

```js
// RepYS (generated): перенос отметок коллекций из repys_collections.js в RYSQuests 0.2.8 (ADR-62). Повтор ничего не меняет.
// Отметки команд: server.persistentData.repys_col.<команда>.<repys:collection/<id>>|<предмет>
// Личные отметки до 18.11: player.persistentData['repys_col/repys:collection/<id>/<предмет>']
function repysColMove(server, owner, key, item) {
  var id = String(key).substring(String(key).indexOf('/') + 1)          // repys:collection/<id> -> <id>
  return RYSQuests.collect(server, String(owner), 'repys:' + id, String(item))
}
ServerEvents.loaded(e => {
  var all = e.server.persistentData.getCompound('repys_col')
  var n = 0
  all.getAllKeys().forEach(team => {
    var tag = all.getCompound(team)
    tag.getAllKeys().forEach(flag => {
      var f = String(flag), bar = f.indexOf('|')
      if (bar > 0 && tag.getBoolean(flag) && repysColMove(e.server, team, f.substring(0, bar), f.substring(bar + 1))) n++
    })
  })
  console.info('repys_collections: отметок коллекций перенесено в книгу ' + n)
})
PlayerEvents.loggedIn(e => {
  var pd = e.player.persistentData
  var prefix = 'repys_col/repys:collection/'
  pd.getAllKeys().forEach(k => {
    var key = String(k)
    if (key.indexOf(prefix) !== 0 || !pd.getBoolean(k)) return
    var rest = key.substring(prefix.length), slash = rest.indexOf('/')
    if (slash > 0) repysColMove(e.server, RYSQuests.progressOwner(e.player), 'repys:collection/' + rest.substring(0, slash), rest.substring(slash + 1))
  })
})
```

## ADR-63 · Лимит закреплённых в окне достижений, подсказки в стиле семьи
Задача автора 18.11, RYSQuests 0.2.8 (черновик). На HUD помещается `hud.max_pinned` карточек (по умолчанию 3); при полном лимите кнопка булавки четвёртого достижения выглядела активной, а сервер молча отказывал.
- Правило лимита одно для сервера и окна (`PinLimit`): квесты и способы делят лимит, выполненный квест место освобождает, повторяемый держит.
- Кнопка булавки в панели достижения в трёх состояниях: «Закрепить на HUD»; закреплено (рамка и значок ярче, подсказка «Открепить с HUD»); нет места (фон карточки, значок `text.dim`, клик ничего не шлёт, подсказка «Закреплено 3 из 3. Открепи одно, чтобы закрепить это»). У закреплённого достижения булавка стоит на карточке в конце строки уровней, с подсказкой «Закреплено на HUD».
- Текстовые подсказки книги рисуются `Kit.tooltip` RYSCore (рамка и шрифт темы) вместо ванильной фиолетовой. Подсказки предметов остаются ванильными: в них описание предмета и строки модов, так и сказано у `Kit.tooltip`.

## ADR-64 · Книга в карточке предмета RYScope: магазин, награды квестов, чип квестов
Запрос автора 18.11 («Осколок Врат»: в RYScope «Источники 0», хотя он продаётся в магазине книги и нужен в двух квестах), план `_shared/_audit/ryscope-quests/PLAN.md`, этап 2, RYSQuests 0.2.8 (черновик). Контракт `works.repka.ryscore.links.ItemLinks` (RYSCore 1.10), потребитель RYScope 0.2.6.
- **Поставщик `client.integration.BookLinks`** (`rysquests:book`) регистрируется при запуске клиента. Категория «Магазин» (`rysquests:shop`, значок блока магазина): сделка, в `gives` которой предмет, идёт в «Источники», сделка, где он в `cost` (цена, продажа, поставка), в «Использования». Категория «Награды квестов» (`rysquests:rewards`): квест, дающий предмет наградой `item` или вариантом `choice`, в «Источники»; случайные награды и таблицы добычи не идут, у них нет точного предмета. Чип: квесты, где предмет в задачах (с тегами `#тег`) или в наградах, считается каждый квест один раз; в списке после квестов строки магазина, в число чипа они не входят.
- **Только то, что видно в книге** (`ItemLinkIndex`, одно место правила): магазин показывает все сделки, закрытые с замком; квест считается, если он живой (не черновик, не архив), стоит в главе, которую книга показывает (не скрытая, сюжетная, не служебная глава наград эпох), и не награда эпохи. Из них скрытый (`hidden`) показывается только после открытия, квест под закрытой стадией не показывается вовсе. Закрытый видимый квест идёт с замком и причиной словами книги. Без раздела магазина или сюжета в `sections` книги соответствующих сведений нет; пустая книга отдаёт пусто.
- **Слова книги.** Карточка сделки берёт имя, цену, замок (`lock_text`, «победи: босс», стадия, квест) и лимит у `ShopView`, поставка показывает доставленное командой из `ClientShop.delivered`. Под замком ссылка на квест, который открывает сделку, если он виден. Действие «Открыть в магазине» открывает книгу на сделке (`BookScreen.openOffer`, фильтры сетки сбрасываются), «Открыть в книге» на квесте (`openAt`).
- **Нагрузка.** Индекс строится один раз на книгу в фоне (`Util.backgroundExecutor`) из одних id; вопрос о предмете это обращение к таблицам, состояние считается только для отданных карточек. Номер версии растёт с новой книгой (`ClientBook.version`), диффом прогресса (`ClientProgress.version`), новым состоянием магазина (`ClientShop.version`) и готовым индексом; открытая карточка RYScope перечитывает сведения только при его смене. Новых пакетов нет.

## ADR-67 · Земля в книге: задача «занять N чанков» и награда «+N к лимиту»
План карты и привата, раздел 8 (RYSQuests: «через `ClaimsApi` позже»), RYSQuests 0.2.11 (черновик). Контракт `works.repka.ryscore.claims.ClaimsApi` (RYSCore 1.11), сервер.
- **Задача `rysquests:claims`** (`task.ClaimTask`, поле `count`): опрос берёт `ClaimsApi.claimed(TeamsApi.teamOf(игрок))`, значение только растёт, как у остальных задач. Считается «пассивной» (сделана тем, что у команды уже есть), считается и заранее (ADR-66). Без RYSClaims `claimed` отвечает 0, задача ждёт.
- **Награда `rysquests:claim_limit`** (`reward.ClaimLimitReward`, поля `claims`, `force_loaded`, `team_mode`): `each` зовёт `addPlayerBonus` (личная добавка уходит с игроком в другую команду, так и задумано контрактом), `once` зовёт `addBonus` команды. Награда из одних нулей не читается. В книге фишка со щитом: «+4 к лимиту земли, +1 к прогрузке».
- **Без RYSClaims** награда выдаётся пустой: лимита нет. Показывать её или нет, решает автор книги; книга RepYS идёт с RYSClaims.

## ADR-66 · Предварительное выполнение закрытых квестов
Запрос автора 19.11: «если условие выполнено, а квест заблокирован, то он засчитывается, но остаётся заблокированным, и при разблокировке сразу засчитанный с наградой». RYSQuests 0.2.10 (черновик). Тот же смысл у FTB Quests: `progression_mode` `flexible` у файла, главы и квеста (`TeamData.canStartTasks`, `Quest.checkForDependantCompletion`), проверено по декомпиляции ftb-quests 2101.1.36.
- **Поле `pre_complete`** у книги (`BookMeta`, по умолчанию `false`), главы и квеста (`Optional<Boolean>`, без поля как у родителя). Правило одно: `QuestLogic.preComplete` берёт ближайшее заданное: квест, глава, книга. Старые книги без поля работают как раньше.
- **Сервер.** Список активных квестов команды (`ProgressService.Active`) держит рядом с открытыми закрытые квесты, которые считают заранее (`QuestLogic.countsEarly`: живой, не сделан, не ждёт повтора, зависимости не выполнены, правило включено). Опрос и события крафта и убийства поднимают их задачи (`QuestLogic.earlyPoll`), но никогда не засчитывают квест. Когда зависимость засчитывается, списки пересобираются (это уже было: смена выполненного сбрасывает кэш), квест переходит в открытые, и первый же опрос засчитывает его по правилу «все задачи сделаны, а квест нет» (`QuestLogic.afterPoll`, ADR от 0.2.1), при входе то же делает `mendStuck`. Отсюда цепочки: каждый следующий квест цепочки засчитывается через опрос (раз в секунду). Стадии остаются правилом каждого игрока: квест за закрытой стадией не считается ни открытым, ни заранее.
- **Сдача не забирается заранее.** Задачи `consume` (предмет, жидкость, опыт) и галочки у закрытого квеста не засчитываются, сдать можно после открытия. Причины: игрок не ждёт, что закрытый квест заберёт вещи, предметы могут понадобиться для зависимостей самого квеста, и у закрытого квеста в книге нет кнопки сдачи. FTB в режиме flexible сдачу разрешает; при импорте такой квест у нас ждёт открытия, это сознательное отличие. Задача `craft` у закрытого квеста считает крафт с момента, как его начали отслеживать.
- **Команда.** Прогресс задач общий, как у открытых квестов: список активных один на команду, считают все её участники.
- **Уведомления.** Тост приходит только при засчитывании, то есть при открытии квеста; рост задач закрытого квеста тостов не даёт, как и у открытого.
- **Вид.** Закрытый квест остаётся закрытым на карте и в панели. В панели над путём к нему тихая врезка: «Условие уже выполнено: квест засчитается, как только откроется» (зелёная галочка), пока не всё сделано, «Задачи засчитываются заранее…» (с оговоркой про сдачу, если она есть); в подзаголовке «пока закрыт · условие уже выполнено».
- **Редактор.** У квеста в «Ещё» и у главы в её форме выбор «Как у главы (вкл)» или «Как у книги (выкл)», «Включено», «Выключено»; в форме главы же переключатель «Во всей книге» (значение книги). Отдельного окна свойств книги нет, а глава это ближайшее место, где автор думает о порядке квестов.
- **Миграции не нужны.** Значения задач хранятся в том же прогрессе; поле читается с умолчанием.
- **Нагрузка** (разбор логики 19.11). Закрытые квесты опрашиваются, только когда есть что читать: предметы и жидкости при смене инвентаря, остальные опрашиваемые задачи вместе со статистикой раз в 5 секунд, убийства и крафт приходят событиями. В список попадает только квест, у которого осталась задача, способная считаться заранее. Разбор предлагал оставить заранее одни предметы; убийства и наблюдение просил автор, поэтому они остались, но реже. Предупреждение в `for-pack-authors.md`.

## ADR-65 · Переезд с FTB шагом ядра: прогресс только добавляется
Этап Я2 плана карты и привата (`_shared/_audit/map/plan.md`, раздел 10.4), разбор `review2.md` (стопор 3), RYSQuests 0.2.8 (черновик), RYSCore 1.11.0 (`migrate.Migrations`).
- **Шаг `quests`, порядок 20** (`integration.ftbq.QuestsMigration`), после шага `teams` RYSTeams. Регистрируется в конструкторе мода. Сам идёт один раз по флагу сборки `config/ryscore/migrate.json` при запуске сервера (после своих миграций книги, `MigrationRunner` на обычном приоритете `ServerStartedEvent`), без флага только `/rys migrate run quests`. Копию FTB и `data/rys*.dat`, отметку `world/rys/migrate.json` и отчёт `[rys-migrate]` делает ядро.
- **Своё не затирается** (`integration.ftbq.FtbqMerge`). Квест, у которого в `rysquests_progress.dat` у команды или игрока есть запись, не трогается, что бы ни говорил FTB; из FTB приходят только квесты без записи. Пустая запись тоже своя: её пишет сброс оператора, и перенос не должен его отменять. Слияние по задачам (`MigrationEngine.best`) отклонено по той же причине. Повтор ничего не добавляет.
- **Ждёт без отметки**, пока стоит FTB Quests (прогресс ведёт он), пока нет таблицы id `config/rysquests/import/ftbq-ids.json` и пока не загружена книга; каждое из этого одной строкой в лог при запуске. Таблица id в RepYS лежит рядом с книгой только у сервера автора: в сборку беты её кладёт генератор (одна строка, задача сборки).
- **Запись.** Перед добавлением своя копия `rysquests_progress.backup-<время>.dat` (как у миграций книги), затем записи, затем `ProgressStore.writeNow`: файл пишется сразу в этом потоке, ошибка роняет шаг, и ядро не ставит отметку (обычное `SavedData.save` пишет в рабочем потоке и только логирует сбой). Файл команды FTB, который не прочитался, пропускается, остальные переносятся, отметка ставится с пометкой «частично».
- **Ручные пути тоже без затирания.** `/rysquests import progress` и перенос прогресса в мастере импорта книги идут через то же слияние вместо `replaceTeam`: повторный импорт книги больше не стирает прогресс, сделанный после первого.
- **Читатель.** `FtbqProgress` читает файлы команд читателем ядра `migrate.Snbt` (флаг `1b` считается единицей); свой `integration.ftbq.Snbt` остаётся у импорта книги. Награды, взятые игроком по квесту, которого в книге нет, больше не заводят пустую запись игрока: в RepYS так ушли бы 309 записей бывших квестов-руководств.
- **Игрок в другой команде** (0.2.9, разбор 18.11, `integration.ftbq.FtbqMembers`). Прогресс FTB лежит по команде FTB, а игрок может играть в другой: он состоял в команде RYSTeams до переезда, и шаг `teams` его не перенёс, или мода команд нет и он играет один. Тогда прогресс его команды FTB складывается и в команду, где он играет сейчас (`ProgressStore.teamOf` по режиму книги), через то же слияние: своё не затирается, из нескольких источников на один квест берётся лучшая запись (`MigrationEngine.best`). Команда FTB сохраняет свою запись, чтобы не потерять прогресс, если её команда появится позже. Личный файл FTB игрока считается его, только если он не был в команде FTB (иначе FTB его скрывал); при переносе из личного файла в команду награды, взятые только им, остаются в его личной записи. Строка отчёта на каждого такого игрока, счётчик `moved`. Состав команд FTB читается из `world/ftbteams/party`; файл, который не прочитался, делает шаг частичным.
- **Частичный шаг** (RYSCore 1.13.1) отметку «сделано» не получает и при следующем запуске идёт снова: слияние добавляет только недостающее.
- **Сервер RepYS** (проверено на копии `RepYS-ServerTest`): прогресс перенесён командой 17.11 и ушёл вперёд. Шаг не меняет ни одной записи, добавляет VENIK четыре незавершённых квеста с частичными задачами из FTB (у команды на них записей нет) и ставит отметку.
